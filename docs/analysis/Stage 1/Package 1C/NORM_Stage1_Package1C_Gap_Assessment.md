# NORM — Stage 1, Package 1C: Focused Gap Assessment

Assessment only · 13 November 2026 · Living document

## 1. Executive finding

**Package 1C can extend the existing batch mechanics.** Multi-file staging, whole-batch confirmation, separate replacement acknowledgement, reinspection, locked predecessor checks and a single acceptance transaction already work in the current implementation. Do not replace them. Package 1A has already added the five-part source identity, permitted/required populations, NULL-ledger handling and Year Setup coverage policy; Package 1B has already supplied the approved native parsers and corrected downloads for accepted sources with failed calculations.

The material extensions are: bind each population to its applicable approved release within one agency; remove the batch's first-release/year persistence assumptions; partition a file only where its supported layout establishes distinct populations; validate/count each partition independently; and make predecessor comparison and source-history access population-based. No accounting aggregation or calculation redesign is needed for source acceptance.

**Ready for bounded implementation authorisation, with a genuine multi-population-file evidence gate.** None of the three approved native profile examples establishes multiple accepted populations within one file. Generic partition mechanics can be implemented and tested with labelled controlled fixtures; this does not establish genuine agency accounting correctness or justify inventing a new layout. A claim of genuine multi-population-file acceptance requires the evidence described in section 6.

## 4. Minimum implementation proposal

One bounded Package 1C, with the following internal testable steps. These are proposals only.

### Step 1 — explicit population and release context

- **Outcome/components:** Extend `NORMImportModels.cs`, `NORMImportService.cs` and the import page's release binding so one active agency contains file results with one or more population previews, each carrying year, company, nullable ledger, stream, exact approved release/fingerprint, coverage and original-file reference. Separate content dimension discovery from configuration-dependent validation in existing parser entry points; keep full parser revalidation after binding.
- **Reuse:** `NORMSourceScope`, content recognisers, approved release loading, population resolution, saved Year Setup, preview lifetime/owner/hash. Prefer minimal adapters over rewriting parsers. A source cannot supply its own agency; configured permitted populations determine authorisation.
- **Acceptance/tests:** Different years resolve to applicable same-agency approved releases; no `first` context is inherited by another year. Multiple candidate releases/population bindings fail clearly until the user selects the applicable approved release for that context using the existing release catalogue. Do not silently choose newest. Test cross-agency denial, missing/deactivated/unapproved/wrong-year release, NULL/0L and ambiguity with substituted configuration.
- **Dependency:** Approved agency/year/population matrix for acceptance; no new policy decision. A release is provenance, never a new source identity. No stream-level user assignments.

### Step 2 — partition and validate before whole-batch confirmation

- **Outcome/components:** Update `InspectSource`, models, relevant existing parser adapters and `AppendSourcePreview` to enumerate populations with separate coverage, counts, controls, errors, totals and predecessor. Partition only at established source dimensions; do not derive streams from accounts or split comparative columns by inference.
- **Reuse:** Native profile controls, exact-zero/storage checks, unmapped warnings, configured resolution, upload-size limit and page confirmation. Keep ActewAGL/Icon native output single-population. Legacy multi-company rows can exercise the partition path with controlled fixtures and explicit row accounting; any genuine native block extension needs its own source evidence.
- **Acceptance/tests:** Every detail belongs to exactly one population; documented metadata/control exclusions reconcile to the file. For a valid batch all detail rows are accepted; for an invalid batch zero are accepted, with invalid rows and valid-but-unaccepted rows distinguished. Reject offsetting non-zero partitions even when file net is zero, within/across-file duplicate identities, account duplicates within a partition and ambiguous populations. Same GL in separate populations is allowed. Test mechanics with labelled fixtures; retain genuine profile counts/hashes without manufactured structures.
- **Dependency:** Section 6 evidence gate limits genuine multi-population claims; it does not block generic partition development.

### Step 3 — atomic acceptance under member contexts

- **Outcome/components:** Extend `ValidateBatchCore`/`ConfirmBatchCore`, `PersistImport` call sites, replacement/rejection audit details and page session validation. Use complete five-part keys. Recheck every distinct release and saved current year, plus all predecessors inside the existing transaction, then persist each population under its own release/year. Use deterministic scope/release lock order.
- **Reuse:** One commit/rollback, single-use previews, source-byte/identity reparse, current-source locks and separate replacement checkbox. Keep calculation after commit and its existing per-import behaviour; do not create a financial aggregate run.
- **Acceptance/tests:** Mixed-year/release new-plus-replacement batch commits all members once or none. Same year/company/ledger/stream in different releases is still a duplicate. Partial and full sources for one identity cannot coexist as batch members. Only saved current year permits partial. Inject later-row/file/audit failure, stale non-first release, year change and predecessor conflict; all pre-existing current IDs/bytes/rows remain unchanged. Verify member release/year/agency/audit parameters.
- **Storage proposal:** Retain one import per population to reuse existing current-source/history lookup and file-level coverage. For a multi-population original, attach its unchanged complete bytes/hash to each affected import, with that import's partition row count and auditable file-detail/partition reconciliation. Do not store fabricated split files as originals. This duplicates bytes but avoids a new shared-file/batch schema; aggregate upload limits count each uploaded file once. Existing nullable-identity and coverage columns suffice for this proposal; do not commission SQL changes without a demonstrated need and the separate migration process.
- **Dependency:** Authorised isolated SQL/browser acceptance later; no deployment or configuration mutation is authorised by this assessment.

### Step 4 — scope history, comparison and missing-population information

- **Outcome/components:** Add focused accepted-population selection/history queries alongside the existing service and workspace; adapt `BuildLatestActivity`/`LoadBalances` only for source comparison. Extend `NORMSourceFileHandler` and source-history links to accepted import/file identity, retaining run/file URLs. Show affected identity, release, original, coverage, operator/time and predecessor; list missing required scopes separately using `MissingRequiredPopulations`.
- **Reuse:** Immutable imports/rows/files, `IMPORT_SOURCE_REPLACED`, parameterised exact-scope predicates, entity access and download auditing. Derive legacy predecessor history using accepted original ordering where a replacement audit is absent; do not relabel unknown legacy streams.
- **Acceptance/tests:** A → B → C history survives unrelated intervening populations and release changes; compare C only with B in the same scope. Zero-balance additions/removals and description changes appear separately from signed financial movement. Fetch every original with matching SHA-256 even with failed or absent run; reject wrong import/file and unauthorised entity. A valid acceptance still succeeds with missing required populations, whose five-part identities remain available to downstream approval controls.
- **Dependency:** No calculation, mapping classification, statement-approval gate or general workspace redesign. Retain the already-correct 1B failed-run path and tests.
